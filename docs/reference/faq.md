# FAQ

## Один endpoint — это отдельный flow?

Нет. Flow появляется не из-за количества endpoint, а из-за самостоятельного сценария и lifecycle.

Список, детали и редактор поста могут стать разными flows, если их логика реально независима.

## Когда `data/posts` оставлять плоским?

Пока файлы легко различать:

```txt
data/posts/
  posts.schema.ts
  posts.dto.ts
  posts.mapper.ts
  posts.store.ts
  posts.types.ts
  index.ts
```

Технические подпапки не нужны заранее.

## Где проверять внешний response?

У владельца данных, внутри `data/<domain>`, до того как значение станет частью store state.

Правило:

```txt
unknown → Valibot → DTO
```

## Зачем DTO, если есть schema?

Schema выполняет runtime-проверку. DTO — статический тип уже проверенного результата.

Обычно DTO выводится из schema через `InferOutput`.

## Может ли DTO входить в public API?

Обычно нет. DTO — внутренняя форма внешнего контракта.

Открывайте его только если внешний потребитель действительно является частью той же границы. Для обычного React UI это почти никогда не нужно.

## Когда нужен mapper?

Когда внешняя форма неудобна приложению.

Например:

```txt
published_at: string
→
publishedAt: Date
```

Если формы действительно совпадают, mapper не обязателен.

## Что хранит MobX store?

Состояние и действия сценария: данные, loading, общую ошибку, computed.

Store не должен хранить JSX или вызывать React hooks.

## Нужно ли хранить поля формы в MobX?

Обычно нет, если форма уже использует React Hook Form.

React Hook Form владеет текущими значениями, touched/dirty и ошибками полей. MobX нужен только для отдельного сценарного состояния.

## Все ли поля React Hook Form нужно оборачивать в `Controller`?

Нет. Обычные inputs лучше подключать через `register`.

`Controller` нужен для компонента с явным `value/onChange`, который нельзя удобно подключить как uncontrolled input.

## Когда нужен `FormProvider`?

Когда глубокие внутренние части одной формы должны получать methods через `useFormContext`.

Для небольшой формы provider часто только добавляет слой.

## Что делает `@hookform/resolvers`?

Связывает внешний validation schema с React Hook Form. Для Valibot используется `valibotResolver`.

## Может ли store читать `useParams`?

Нет. React hooks вызываются в React-компонентах.

Page читает `postId` через React Router и передаёт его дальше обычным значением.

## Где выполнять navigation после сохранения?

В React-слое через React Router.

Store может вернуть идентификатор сохранённого поста:

```txt
save(values) → postId
```

А компонент решает:

```txt
navigate(`/posts/${postId}`)
```

## Когда компоненту нужен `observer`?

Когда он прямо читает observable/computed MobX state.

Dumb-компонент, который получает обычные props, обычно не требует `observer`.

## Может ли `components/ui` импортировать `data`?

Лучше нет. `ui` — dumb layer.

Если компонент читает store, это smart-компонент и его стоит разместить в `widgets` или другой явно smart-части модуля.

## Когда нужен view model?

Когда одному представлению нужно вычисляемое read-only представление сразу нескольких stores.

Если достаточно пары props, VM не нужна.

## Нужен ли RootStore?

Не автоматически.

RootStore оправдан, если он решает реальную задачу композиции и lifecycle. Один объект ради доступа ко всем stores обычно только усиливает связанность.

## Где хранить provider?

Рядом с владельцем его lifecycle.

`PostEditorProvider`, нужный только редактору, не должен жить в корне приложения.

## Что относится к `shared`?

Код, который не знает, что приложение — блог.

`Button` может быть shared. `PostCard` — нет.

## Нужно ли делить pages на `public/private`?

Только если это отражает реальную структуру маршрутов проекта.

DSA не требует создавать пустые группы заранее.

## Как читать стрелку зависимостей?

```txt
pages → components
```

означает: `pages` может знать `components`, но `components` не должен импортировать `pages`.

Даже `import type` считается зависимостью.
